## 3. Ordre de travail concret

1. **Un seul checkout backend d'intégration** depuis le backend de .84 ou le SHA plus récent confirmé par les pins actuels, sans modifier le backend utilisateur. Lire status/remotes et conserver les modifications concurrentes.
2. **Reprendre AH-345/AH-346 une seule fois**. S'ils sont encore non commités, exporter leurs seuls fichiers en patch, `git apply --check` dans l'intégration puis appliquer ; s'ils ont été commités, cherry-pick les commits exacts. Ne jamais appliquer patch et cherry-pick du même changement. AH-345 touche TRT, AH-346 pipeline : intégrer leurs deux commits distincts facilite les reçus.
3. **Compiler les modules depuis le SHA intégré** ou consigner explicitement une provenance différente par module si réutilisation contrôlée. Vérifier les builds candidats et ne pas emballer un build hôte incompatible avec la baseline portable. Le CMake TRT alias est identique ; le pipeline facultatif TrueHDR doit garder la capacité requise. Ne pas perdre les suppressions FRUC/Spline36 de .84.
4. **Compléter la décision du planificateur si elle manque** : pour chaque groupe, enregistrer stages/IDs, blocs réels, ordre, géométrie, policy et raison de frontière. Utiliser des raisons explicites telles que Fast×2 séparé, resize attaché changerait l'ordre, provider incompatible, deuxième interpolation non représentable par ABI9, HDR/Area terminal. Ce diagnostic est destiné aux journaux/exports, pas un choix technique imposé dans le profil utilisateur.
5. **Vérifier les gardes existantes avant d'en créer d'autres**. Si elles répondent déjà au contrat, documenter et livrer le travail manquant utile ; ne pas ajouter une couche de planification générale sans besoin. Si un élargissement de fusion est envisagé, ouvrir une sous-tâche bornée décrivant le bloc exact, référence numérique et coût attendu ; ne pas l'activer par défaut sur une intuition.
6. **Livrer puis vérifier** les enfants et l'orchestration. Consigner la décision globale avec les limites du lot55, pas une somme de microgains annoncée comme gain de lecture.

## 4. Invariants que toute refonte doit garder

- Profil libre : ordre/activation/modèles/policies/dimensions/facteurs appartiennent au profil. Aucun tri silencieux des catégories, aucun profil intégré imposé.
- Groupement logique interpolation/upscale ≠ bloc natif unique. Plusieurs RIFE peuvent nécessiter plusieurs contextes. Resize/HDR/providers incompatibles restent des frontières ; étapes désactivées ne créent pas une opération cachée.
- Fast×2 reste séparé jusqu'à nouvelle preuve suffisante **sur un candidat différent utile**. Ne pas relancer à l'identique les variantes déjà rejetées pour chercher un résultat favorable.
- Quality exécute la prédiction complète pour chaque phase nécessaire ; aucune substitution motion-only, held frames approximatives, baisse de résolution ou suppression de quantification. Fast>3 reste approximation explicitement choisie.
- ABI9 remonte le resize attaché au premier upscaler avant RIFE. La garde empêche une fusion qui changerait l'ordre explicite ; les pourcentages sont des doubles, donc100.5 n'est pas100. Conserver traitement des non-finis.
- Fréquences/facteurs : chaque étage conserve son facteur, facteur cumulé limité selon le contrat, PTS rationnels/durées/EOF exacts ; route legacy équivalente garde ses fractions. Ne pas arrondir un facteur mixte indisponible ni tomber silencieusement vers une ancienne route.
- Cache valide seulement avec identités/générations/vues/color/format/stream compatibles ; pointeur GPU seul ne constitue pas une identité. Reset invalide les données logiques, préserve fences nécessaires ; erreur/cancel/drain ne libère pas un owner en vol.
- Le pixel_budget borne le pool possédé, pas toute la VRAM. Ne pas augmenter le budget pour masquer une rétention excessive, ni annoncer une limite globale de mémoire.
- TrueHDR reste à sa place autorisée après moteurs SDR. Déplacer HDR avant interpolation est AH-333 distinct. Chaque backend peut conserver ses formats/kernels/langages adaptés ; absence d'API/hardware = portée partielle, pas convergence forcée.

## 5. Vérifications ciblées

Contrôle CPU existant du plan (à lancer après changement de décision, pas à chaque simple lecture) depuis le checkout backend d'intégration :

```bash
c++ -std=c++17 -O2 -Iinclude -Isrc tests/pipeline_execution_test.cpp \
  src/pipeline_config.cpp src/aji_conf.cpp -o /tmp/ah208-pipeline-execution-check
/tmp/ah208-pipeline-execution-check
```

Il couvre groupes1/2/4maillons, frontières, disabled, policies/ordre, exception Fast2. Si une garde change, ajouter uniquement le cas absent pertinent. Pour la compatibilité legacy/fractions, le test existant prend un répertoire temporaire :

```bash
c++ -std=c++17 -O2 -Iinclude -Isrc tests/pipeline_config_test.cpp \
  src/pipeline_config.cpp src/aji_conf.cpp -o /tmp/ah208-pipeline-config-check
AH208_FIXTURE=$(mktemp -d /tmp/ah208-config-check.XXXXXX)
/tmp/ah208-pipeline-config-check "$AH208_FIXTURE"
```

Les copies finales AH-346 : vérifier que leur source `points` et les sorties du job restent possédées jusqu'à l'attente finale ; tous les chemins de succès/erreur gardent le drainage approprié. **Ne pas supprimer les synchronisations inter-contextes** parce que le worker est unique : leurs streams sont différents.

Revue+build suffisent pour suppression statique démontrée. Une nouvelle fusion qui change des frontières numériques, ressources ou stratégie temporelle mérite seulement l'ablation courte capable de lever ce doute. Employer `tests/inference/pipeline_fusion_probe.py` avec JSON, `AJI_PIPELINE_TRACE=1` et destinations nouvelles ; reprendre le guide AH-329 pour les champs/limites de la sonde. Aucun GPU concurrent. Même entrée/réglages/machine, arrêt dès conclusion suffisante.

Ablation actuelle : `AJI_PIPELINE_FUSION=0`. Limite : elle sépare RIFE/upscale compatible, mais continue de regrouper certains upscalers consécutifs ; ce n'est pas une référence «tous les stages séparés». Le cas lot55 quatre maillons utilisait identité×1→Q2→F2→SPAN, pas deux vrais upscalers×2. Toute revendication sur cette dernière chaîne demande une référence définie.

Les compteurs pipeline sont des requêtes ; ni nombre de kernels ni FPS. Une réduction de barrières ne prouve pas le gain total si HDR domine. Une compilation sur plusieurs architectures ne prouve pas l'exécution de chacune.

## 6. Livraison, erreurs et Done

En cas d'option/provider/facteur non supporté : conserver profil et diagnostic explicite. En cas d'absence de build/SDK : distinguer module non compilé, capacité absente et runtime indisponible. Ne pas désactiver une validation pour obtenir une exécution trompeuse.

Publier sources backend et modules ciblés, bundle issu du pin courant, manifeste avec provenance par module, pin PLAYER exact, release suivante avec artefacts vérifiés. Pas de `git add -A`, pas de push vers origin local du backend utilisateur, pas d'écrasement d'une release existante. Guide de livraison détaillé AH-345 disponible ; les archives .82/.83 restent des preuves datées.

Done seulement si le garde de décision et son diagnostic sont concrets, les enfants retenus sont livrés/vérifiés, Fast4 conserve sa stratégie utile, Fast2 sa séparation et Quality sa référence ; les nouvelles variantes éventuellement retenues ont la preuve adaptée et les reliquats explicites. Le parent reste ouvert si son périmètre global est encore partiel. Écrire séparément coût supprimé par code, gain attendu et gain mesuré ; ne jamais annoncer une addition de microgains comme FPS de lecture.
