Ne pas refaire ces fonctions sous un autre nom. Le problème restant est de les raccorder au **module/policy réellement sélectionné et chargé**.

## 3. Relever la référence effective en lecture seule

Sélectionner explicitement l'instance mpv concernée, sans arrêter ou reconfigurer la lecture utilisateur. Exemple Linux, après choix de son PID :

```bash
pgrep -a -x mpv
AH330_PID=12345
readlink -f "/proc/$AH330_PID/exe"
rg 'libaji[^ ]*\.so' "/proc/$AH330_PID/maps"
```

Remplacer12345 par le PID vérifié, jamais le premier résultat supposé. Ce relevé montre les chemins/identités mappés ; il ne prouve pas à lui seul le hash des pages d'un fichier remplacé après chargement. Si une ligne est `(deleted)`, si l'inode a changé ou si le fichier est modifié pendant le relevé, noter la provenance du binaire chargé inconnue et utiliser un nouveau processus de contrôle isolé, sans tuer le lecteur utilisateur.

Avec le helper installé explicitement choisi :

```bash
/chemin/verifie/AnimeJaNaiPlatform --versions --root /racine/installation/verifiee
/chemin/verifie/AnimeJaNaiPlatform --export-reference \
  --root /racine/installation/verifiee --mpv-ipc /socket/mpv/verifie \
  --output /tmp/ah330-reference-unique.json
```

Ces chemins sont à relever dans la session, pas à deviner. L'export est en lecture seule et refuse les modifications de l'état observé. Il fournit profil/règle/vf/options/fichiers ; ne transformer ni son inventaire disque ni une ancienne ligne de stats en attestation du module chargé. Ne pas exécuter `--activate-bank`, `--save-bank`, installer ou modifier les profils pour cette observation.

## 4. Implémentation recommandée, en étapes séparables

Mettre AH-330 In Progress, créer un checkout PLAYER isolé depuis le SHA de .84 ou son successeur confirmé. Ne pas éditer le checkout d'intégration Manager encore détenu par un autre agent. Backend utilisateur original interdit en écriture.

### A. Rendre la décision observable

Produire un diagnostic unique par activation/reconfiguration : backend demandé, module dispatcher/alias demandé, chemin résolu du module moteur, provenance/hashes disponibles, version/capacités de sémantique Quality, policy demandée et policy effective, origine «paquet géré / override explicite / fichier non attribué», décision de compatibilité. Le résolveur statique ne doit pas prétendre qu'un fichier présent est déjà chargé.

Réutiliser les métadonnées du filtre (`MP_FILTER_COMMAND_GET_META`, tags existants), journaux et export de référence. Si un backend expose une API facultative de provenance/capacité, la versionner et tolérer son absence pour les diagnostics ; absence signifie **inconnu**, pas «compatible». Sous Linux, le code du module peut identifier sa propre image avec les mécanismes déjà utilisés (`dladdr`/`own_dir`); sous Windows la route a ses propres handles/API. Ne pas forcer une même implémentation bas niveau partout. Hash à l'activation ou sur demande, pas à chaque image.

### B. Garantir Quality avant lancement

Un profil `old` ou `quality` doit soit sélectionner un moteur qui garantit les prédictions complètes, soit refuser cette route avec une action claire (utiliser le module géré courant / expliciter l'override / mettre à jour). Ne jamais conserver le libellé Quality en autorisant un backend dont la policy effective est Fast ou inconnue.

L'alias `old` était compris par l'ancien parseur : une projection dans une **configuration privée générée** peut être une compatibilité bornée pour une version identifiée, mais elle ne suffit pas à certifier tous les autres raccourcis d'un binaire inconnu. Ne pas remplacer globalement `quality` par `old` dans les profils utilisateur. Vérifier le contrat effectif du module choisi ; préférer la route gérée compatible si l'installation la possède et que l'override n'était pas explicite, sinon diagnostic/refus contrôlé. La preference Fast reste distincte et opt-in, pas un fallback automatique.

### C. Traiter les fichiers locaux sans les écraser arbitrairement

Distinguer : lien géré, fichier géré dont l'empreinte ancienne est connue, override explicite, fichier régulier non attribué. Un fichier régulier n'est pas automatiquement géré ni jetable. Pour une migration d'un fichier géré identifié : sauvegarde ciblée avec reçu, remplacement atomique, manifeste mis à jour seulement après succès, reprise idempotente. Pour override/inconnu : préserver les octets et le chemin, expliquer incompatibilité et action ; ne pas le supprimer pour faire disparaître le diagnostic.

Ne pas déplacer/supprimer SDK, modèles, caches, profils ni toute l'installation. Ne pas lancer AppRun complet dans une fixture où il pourrait télécharger des packs : isoler/tester la décision de résolution/migration. Maintenir les aliases réellement consommés tant que les lecteurs les utilisent. `libaji_trt_rtx.so` est aujourd'hui un alias binaire de TRT, `libaji_rtx.so` est un helper SDK différent : ne pas les confondre.

## 5. Contrôles nécessaires et commandes simples

Pas de benchmark vidéo : défaut de chargement/policy, pas optimisation d'inférence. Utiliser un arbre d'installation temporaire avec copies factices ou modules de fixture, jamais les composants utilisateur :

1. Liens gérés normaux vers paquet courant : route actuelle correcte, Quality garanti.
2. Fichier régulier ancien identifié + module géré récent : aucune sélection silencieuse incompatible, migration ou choix/refus prévu, octets d'origine sauvegardés si migration.
3. Override explicite/inconnu : contenu préservé, origine visible, Quality protégé ; Fast demandé reste distinct.
4. Manifeste absent/mauvais hash/module manquant/permission refusée : diagnostic déterministe et repli contrôlé, pas faux statut compatible.
5. Nouvelle exécution après migration : preuve du module réellement chargé et policy effective ; la présence du nouveau fichier seule ne suffit pas. Interruption de migration et répétition : état sûr/idempotent.

Ajouter seulement les tests absents du correctif. Réutiliser tests CPU existants de projection/policy, qui ne prouvent pas à eux seuls le chargement natif :

Ne pas prétendre avoir exercé Windows/macOS en exécutant des fixtures Linux ; les simulations de selection statique sont à nommer comme telles. Un petit harness natif qui charge des modules de fixture suffit au routage/diagnostic ; si seul le module GPU réel révèle une incertitude de policy, une exécution ciblée Quality suffit, aucun benchmark de FPS requis.

Ce test prouve le parseur compilé, pas la version d'une bibliothèque déjà installée.

Conserver les changements par composant : PLAYER pour résolution/diagnostic/migration, backend seulement si API/protection nécessaire, Manager uniquement si exposition existante à compléter. Aucun nouveau profil imposé.

Commit de fichiers explicites, sources isolées ; contrôler les remotes avant push (certains clones backend ont origin local). Bundle depuis pin courant pour les modules recompilés seulement, provenance exacte par module, pin PLAYER, release suivante, extraction/vérification des assets. Conserver les fichiers utilisateur et enregistrer la migration éventuelle ; vérifier une installation de contrôle mise à jour, pas seulement une compilation.

Done quand : un paquet neuf et un ancien fichier local ne peuvent plus annoncer/exécuter Quality comme Fast sans diagnostic/action ; provenance du module effectivement chargé observable ; liens gérés et overrides sont préservés/migrés selon leur statut ; aliases ont leur vraie sémantique ; les routes affectées et erreurs sont contrôlées ; livraison vérifiée. Documenter le matériel/OS non exercé. Aucun gain FPS attendu pour ce correctif de fidélité ; AH-329 peut ensuite utiliser une référence Quality crédible, sans conclure que toute la baisse antérieure est expliquée.
