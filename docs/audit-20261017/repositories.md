## Couverture à compléter avant la refonte Manager

1. **Frontières entre dépôts et plateformes** : versions effectives des sources partagées C#, capacités réellement livrées Linux/Windows/macOS, contrats de configuration, routage et migration. Priorité à la cohérence exécutable du plan de profil avant présentation UI.
2. **Backend complet du projet** : auditer dispatcher, DML, ancien helper RTX, branches de build et erreurs/repli ; compléter les caches, budgets et conventions de couleur au-delà des chemins RIFE/TensorRT déjà revus.
3. **Moteurs du PLAYER non CUDA** : revue séparée de Vulkan/NCNN, ORT/OpenVINO, MIGraphX/HIP et CoreML/Metal, de leurs conversions, caches, thread pools, coûts de transfert et capacités. L’audit des seules déclarations CMake n’est pas suffisant.
4. **Fork mpv et construction du lecteur** : vérifier le code assemblé à partir du pin + patchs ; examiner le delta spécifique des forks mpv/libass et les différences de livraison Windows/macOS. Un audit global de tout FFmpeg/libplacebo n’est pas revendiqué ; cibler les interfaces réellement utilisées et le comportement attendu.
5. **Manager/updater/installateurs** : compléter services et transitions/annulations/migrations, séparer code mort confirmé et ressources chargées via XAML/réflexion, puis préparer la refonte entière selon les défauts déjà prouvés. Pas de refonte UI lancée par cette cartographie.
6. **Documentation multi-dépôts** : le nettoyage PLAYER ne suffit pas. Backend `aji-rtx-linux/README.md` et docs Manager doivent distinguer routes livrées, prototypes et limitations. Les qualifications historiques restent des preuves datées, pas des descriptions du produit courant.
