## 2. Comprendre exactement ce qui a changé

Pour un facteur RIFE num/den >3+1e-9, le Fast existant utilisait déjà une seule inférence de mouvement à t=.5 pour toutes les phases, quelle que soit l'amplitude. Il calculait néanmoins un maximum du flot, le copiait vers le CPU et attendait cette copie. Le patch supprime ce calcul inutilisé et fait porter sa dépendance de fin par un événement CUDA.

Économie démontrée par lecture du code, par nouvelle paire Fast >3 : un memset scalaire, un kernel de maximum lisant quatre composantes half pour chaque pixel du flot (8×W×H octets logiques lus), une copie D2H et une attente hôte scalaire. À1280×720, le kernel parcourait 7 372 800 octets logiques. **Ce nombre ne mesure ni trafic DRAM ni gain en millisecondes.** Les inférences RIFE et upscaler, le modèle, les poids, le timestep .5, le masque, le warp et le blend sont conservés.

Le champ `motion_done` est ajouté à l'état warp, créé avec les ressources overlap pour les seuls facteurs >3, enregistré après l'inférence motion et attendu dans le stream appelant **après** soumission des upscales. Les facteurs2/3 gardent leur branche adaptative et leur score ; Quality reste sur les prédictions RGB complètes. La règle de non-fusion Fast×2 reste intacte.

Autres pistes de l'audit (pads YUV inutilisés, barrières finales du pipeline) sont distinctes : ne pas les ajouter à ce patch. DirectML AH-344 est géré séparément.

## 3. Invariants de synchronisation déjà revus

Conserver ces preuves dans le ticket, sans inventer de qualification GPU :

- **Même stream :** le wait de `motion_done` est déjà en file sur le stream appelant avant que `aji_infer_rife` rende la main. Le warp consommateur et le prochain remplissage de `R.in_tensor` y seront ordonnés après lui.
- **Changement de stream entre appels :** `order_inference_stream` est appelé avant la préparation. Il enregistre `work_order` sur l'ancien stream, ce qui capture aussi son wait motion, puis le nouveau stream attend `work_order`. Les resets gardent ce fence.
- **Pas d'overlap / création d'event impossible :** destruction des ressources overlap partielles, pointeurs remis à null ; tout est exécuté dans le stream appelant, dont l'ordre suffit. Aucun wait-event avec un event null.

Il ne devient true qu'après transfert correct de la dépendance au stream appelant (ou exécution ordonnée sur stream unique). Les erreurs Surface drainent aussi le device.
- **Reset / reconfigure / destruction :** reset invalide les identités sans effacer le fence `work_order`; configure et destroy synchronisent le device avant de libérer tenseurs/event. `motion_done` est détruit avec les autres ressources motion.
- **Réenregistrement d'event :** l'en-tête SDK local `/opt/cuda/include/cuda_runtime_api.h:2894–2908` documente que `cudaStreamWaitEvent` retient l'état le plus récemment enregistré lors de son appel ; les records ultérieurs ne modifient pas cette attente.
